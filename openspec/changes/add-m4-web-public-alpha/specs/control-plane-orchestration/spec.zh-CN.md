## 新增需求

English version: [spec.md](spec.md)

### 需求：带版本、不可变的数据任务规格
系统必须交换 JSON 兼容的不可变数据任务规格，其中包含模式版本、稳定任务 ID、工作空间 ID、项目 ID、任务类型、输入引用、确定性配置、请求的 engine/runtime、输出目标、attempt 编号和幂等键。规格中不得出现凭据，只允许限定范围的秘密引用或对象引用。

#### 场景：重复提交同一命令
- **当** 客户端使用相同工作空间幂等键和等价载荷重复创建任务
- **则** 控制面返回同一任务身份，且不创建第二次执行

#### 场景：拒绝变化的幂等命令
- **当** 客户端用同一幂等键提交语义不同的载荷
- **则** 控制面以幂等冲突拒绝请求

#### 场景：任务不携带凭据
- **当** 任务需要访问受保护的输入或输出
- **则** 规格只包含 Worker 可解析的受限引用，不包含访问密钥、密码或 Bearer Token

### 需求：权威产品任务生命周期
控制面必须执行 `queued → leased → running → succeeded | failed | cancelling → cancelled` 生命周期，阻止状态倒退，并记录每次接受迁移的任务身份、attempt 身份、操作者、时间和关联 ID。

#### 场景：完成发布任务
- **当** 运行中的发布任务上报成功
- **则** 只有同时提供终态 Domena `JobRun` 证据和经验证的 `MaterializationReference` 才能接受迁移

#### 场景：请求取消
- **当** 用户取消排队任务
- **则** 任务无需 Worker 执行即可变为已取消

#### 场景：取消运行中的工作
- **当** 用户取消运行中的工作
- **则** 任务进入取消中，直到 Worker 确认取消或上报终态失败

#### 场景：收到过期事件
- **当** 旧 attempt 的事件会使已接受状态倒退或被替换
- **则** 控制面拒绝或幂等忽略该事件，并保留当前状态

### 需求：有界 Worker 租约与重试
控制面必须把排队任务按有界时间租给经过认证的 Worker。租约必须标识唯一不可变 attempt 和租约 Token。未终态的过期工作可以重新排队；每次重试创建新 attempt，同时保留稳定任务身份和历史 attempt 证据。

#### 场景：Worker 租用可用任务
- **当** 兼容且授权的 Worker 请求工作，并存在排队任务
- **则** 控制面原子创建 attempt、授予唯一租约，并阻止其他 Worker 租用同一 attempt

#### 场景：无终态证据时租约过期
- **当** Worker 停止心跳且租约过期
- **则** attempt 被标记为过期，策略可以将任务重新排队，但不得删除 attempt 证据

### 需求：工作空间隔离与授权
每个产品资源必须属于工作空间，并在适用时属于项目。面向用户和内部 API 在返回元数据、发放对象访问或改变状态前，都必须检查认证主体权限。对于无权限调用方，跨工作空间标识应当与不存在的资源不可区分。

#### 场景：访问其他工作空间的 Release
- **当** 用户提供一个属于无权访问工作空间的有效 Release ID
- **则** API 不返回 Release 数据，也不发放对象存储授权

### 需求：单一数据库所有者
Go 控制面必须是唯一写入 PostgreSQL 控制面状态的应用组件。Python Worker 必须通过经过认证的内部 API 租用工作并上报进度或终态证据，且不得获得数据库直写凭据。

#### 场景：Worker 发布终态证据
- **当** Python Worker 完成任务
- **则** 它向内部 API 提交带版本的终态证据，由 Go 控制面验证并事务化提交状态

### 需求：兼容 M3 执行证据
编排层必须保留 M3 数据面产生的输入 Release 指纹、处理指纹、engine 名、runtime 名、失败证据和物化证据，不得仅凭进程退出推断发布成功。

#### 场景：进程成功退出但没有物化
- **当** 发布 Worker 以代码零退出但未提供经验证的物化证据
- **则** 控制面不得把任务标记为成功
